# Сервис учёта бытовой техники

Учебное приложение для ведения домашнего или офисного реестра техники.
Консольная версия, созданная в ПР1–ПР3, дополнена в ПР5 базовым
веб-интерфейсом на Django. В ПР6 веб-часть переведена на Django Template
Language (DTL): HTML находится в шаблонах, а представления подготавливают
данные и передают их через контекст в `render()`.
В ПР7 веб-часть получает данные из SQLite через стандартный модуль `sqlite3`
и параметризованные SQL-запросы. Исходные JSON и консольная версия сохранены.

## Возможности

Веб-интерфейс позволяет:

- просматривать список устройств;
- открывать карточку устройства;
- видеть состояние и рекомендацию по обслуживанию;
- просматривать помещения;
- видеть устройства выбранного помещения;
- переходить между связанными страницами;
- получать понятные страницы с кодом HTTP 404.
- искать технику по названию, типу и производителю;
- сочетать фильтры по помещению, состоянию и максимальной стоимости;
- искать исправные устройства, выбрав соответствующее состояние;
- находить помещения без действующей техники;
- просматривать статистику стоимости и количества устройств, группировку
  по помещениям и состояниям, список техники для обслуживания.

Консольная версия дополнительно поддерживает добавление, поиск, сортировку,
фильтрацию, изменение и удаление устройств, назначение помещений и статистику.

## Предметная область

- `Device` — устройство с названием, типом, производителем, моделью, годом,
  стоимостью, состоянием и интервалом обслуживания;
- `Room` — помещение, в котором находится техника;
- `User` — пользователь консольного приложения.
- `Condition` — справочник состояний техники в SQLite.

Объект `Device` содержит ссылку на объект `Room`. Классы ПР3 остаются в
`models.py` и пока не являются моделями Django ORM.

## Страницы веб-интерфейса

| URL | View-функция | Назначение |
|---|---|---|
| `/` | `homepage.views.index` | Главная страница |
| `/devices/` | `equipment.views.device_list` | Список устройств |
| `/devices/<int:device_id>/` | `equipment.views.device_detail` | Карточка устройства |
| `/devices/search/` | `equipment.views.device_search` | Поиск и фильтры техники |
| `/devices/statistics/` | `equipment.views.statistics` | Агрегаты и группировка |
| `/rooms/` | `rooms.views.room_list` | Список помещений |
| `/rooms/<int:room_id>/` | `rooms.views.room_detail` | Карточка помещения |
| `/rooms/available/` | `rooms.views.available_rooms` | Помещения без действующей техники |

Для неизвестного URL используется `homepage.views.page_not_found`. Если
динамический URL существует, но объект с переданным ID отсутствует,
соответствующая view-функция возвращает собственную страницу со статусом 404.
В шаблон карточки при этом передаётся `None`, и сообщение выводится через
`{% if %}` / `{% else %}` с сохранением HTTP-статуса 404.

## Шаблоны Django (ПР6)

Общие шаблоны находятся в `templates/`, а шаблоны приложений — в их каталогах
`templates/<имя приложения>/`. В `settings.py` настроены
`"DIRS": [BASE_DIR / "templates"]` и `APP_DIRS=True`.

Все страницы наследуют `base.html` через `{% extends "base.html" %}` и
переопределяют блоки `{% block title %}` и `{% block content %}`.
Веб-представления больше не формируют HTML-строки; функции `page()` и
`html_response()` удалены.

Повторяющиеся части подключаются через `{% include %}`:

- `includes/navigation.html` — общая навигация с активным разделом;
- `rooms/includes/room_card.html` — карточка помещения;
- `equipment/includes/device_card.html` — устройство в общем списке и помещении;
- `equipment/includes/device_condition.html` — состояние устройства в карточках
  и на подробной странице.

В ПР7 представления передают строки `sqlite3.Row` через словарь контекста.
Столбцы SQL доступны в Python как `row["name"]`, а в DTL как `row.name`.
Связанные поля устройства получены через JOIN: `device.room_id`,
`device.room_name`, `device.condition`. В списке помещений `room_cards`
содержит строки помещений вместе с подсчитанным в SQL числом устройств.
Данные включаемым карточкам передаются явно через `with ... only`.

Списки формируются через `{% for %}`, отсутствие данных обрабатывается через
`{% empty %}`. Условия `{% if %}` выбирают цвет состояния устройства,
сообщение о доступности и ветку отсутствующего объекта. Рекомендации по
обслуживанию вычисляются существующим методом `Device.get_service_status()`
во view, а не средствами шаблона.

Фильтры применяются к данным проекта:

- `{{ devices|length }}` и `{{ rooms|length }}` — количество элементов;
- `{{ room.name|default:"Без названия" }}` — запасной текст;
- `{{ device.price|floatformat:"2" }}` — стоимость с двумя десятичными знаками;
- `{{ device.purchase_year|stringformat:"d" }}` — год без разделителя тысяч.

Django автоматически экранирует пользовательские данные при выводе.

## Хранение данных

Используются два отдельных файла базы данных:

- `data/appliances.sqlite` — предметные данные ПР7: `rooms`, `users`,
  `conditions`, `devices`. Веб-представления читают именно эту базу.
- `db.sqlite3` — служебные таблицы Django: администраторы, сессии и права.
  Настройка `DATABASES` по-прежнему указывает на неё. Она исключена из Git.

Путь предметной базы задан в `APPLIANCES_DB_PATH` в `settings.py` и считается
от корня проекта, поэтому не зависит от текущего рабочего каталога.
`get_connection()` включает `PRAGMA foreign_keys = ON`, задаёт
`connection.row_factory = sqlite3.Row`. Соединения закрываются после запроса.
При отсутствии базы сайт не создаёт пустой файл: нужно выполнить импорт.

Таблицы и ограничения определены в `sql/schema.sql`:

| Таблица | Поля | Связи и ограничения |
|---|---|---|
| `rooms` | `id`, `name` | PK, уникальное непустое название |
| `users` | `id`, `login`, `password` | PK, уникальный непустой логин |
| `conditions` | `id`, `name` | PK, уникальное непустое состояние |
| `devices` | `id`, `name`, `device_type`, `manufacturer`, `model`, `purchase_year`, `price`, `room_id`, `condition_id`, `service_interval` | PK, два FK, стоимость >= 0, интервал > 0 |

Все поля обязательны (`NOT NULL`); поля с отсутствующими значениями текущей
предметной области не требуются. `service_interval` имеет значение по умолчанию
3. Удаление используемого помещения или состояния запрещено (`RESTRICT`).
Для внешних ключей устройств созданы индексы. Пользователи сохраняются
отдельной таблицей: ранее связи между пользователем и устройством не было.
Веб-авторизация в ПР7 не добавлялась.

Исходные `data/*.json` сохранены. `python -m db.import_json` создаёт таблицы
без удаления существующих, переносит записи с исходными ID и преобразует
`room_name` и название состояния в внешние ключи. Данные проверяются классами
ПР3. К трём состояниям JSON добавляется уже поддерживаемое классом `Device`
состояние «списано». Новые записи вставляются через `executemany()`;
после успешного импорта вызывается `commit()`, при ошибке — `rollback()`.
Повторный запуск пропускает полностью совпадающие записи. При конфликте
значений или повторяющихся ID импорт останавливается и откатывает вставки,
не перезаписывая существующие данные.

Консольная версия продолжает работать с JSON через `storage.py`, `Device`,
`Room`, `User`. Между JSON и SQLite нет автоматической синхронизации:
изменения в консоли не меняют уже импортированную веб-базу.

## SQL-запросы ПР7

Все 12 запросов находятся в `sql/queries.sql` с комментариями и именами
`-- name: ...`. Модуль `db.queries` загружает их без копирования SQL во views.
Значения из HTTP передаются отдельным кортежем в `execute(sql, parameters)`
через заполнители `?`. Конкатенации пользовательских значений с SQL нет.

| № | Имя | Страница / назначение | SQL |
|---|---|---|---|
| 1 | `rooms` | Список помещений, варианты формы | SELECT, LEFT JOIN, COUNT, GROUP BY |
| 2 | `devices` | Список техники | SELECT, два JOIN, ORDER BY |
| 3 | `room` | Карточка помещения | WHERE по ID |
| 4 | `device` | Карточка устройства | JOIN, WHERE по ID |
| 5 | `room_devices` | Техника помещения | JOIN, WHERE |
| 6 | `conditions` | Состояния в форме поиска | SELECT, ORDER BY |
| 7 | `search_devices` | Поиск и сочетание фильтров | JOIN, WHERE, LIKE, AND, OR |
| 8 | `device_totals` | Общая статистика | COUNT, SUM, AVG, MIN, MAX |
| 9 | `room_statistics` | Статистика помещений | LEFT JOIN, GROUP BY, HAVING |
| 10 | `condition_statistics` | Статистика состояний | LEFT JOIN, COUNT, SUM, GROUP BY |
| 11 | `service_due` | Список для обслуживания | WHERE, NOT IN, несколько условий |
| 12 | `empty_rooms` | Помещения без действующей техники | NOT EXISTS, JOIN |

Выполнен минимум: более 10 запросов; не менее двух выборок списков,
фильтраций WHERE, соединений JOIN, агрегатных запросов и группировок GROUP BY.
Все запросы используются веб-страницами и проверяются тестами.

Сценарий «поиск свободных помещений на дату» из примера Roomly адаптирован:
в учёте техники нет бронирований и дат занятости. Реализован поиск исправных
устройств и помещений без действующей техники. Списанное устройство не делает
помещение занятым и не включается в стоимость действующей техники. Пустые
помещения и состояния без устройств сохраняются в статистике через LEFT JOIN.

Примеры URL:

```text
/devices/search/?condition=исправно
/devices/search/?q=Samsung&room_id=2&max_price=53000
/devices/statistics/?min_count=2
/rooms/available/
```

Форма проверяет числовые значения, диапазоны и допустимость выбранных
помещений/состояний. Ошибки показываются на странице без HTTP 500.
В поисковом тексте `%`, `_` и `\` экранируются как обычные символы.
Стандартный SQLite LIKE не учитывает регистр латиницы, но различает регистр
кириллицы: для поиска по названию «Холодильник» используйте «Холод»,
либо ищите по латинскому производителю.

Проверка всех запросов с параметрами:

```bash
python -m db.check_queries
```

Для просмотра структуры и выполнения SQL в SQLite CLI:

```bash
sqlite3 data/appliances.sqlite
.tables
.schema devices
SELECT COUNT(*) FROM devices;
```

Если отдельный `sqlite3` не установлен, в Python 3.12+ доступна консоль:

```bash
python -m sqlite3 data/appliances.sqlite "SELECT COUNT(*) FROM devices;"
```

Таблица `users` содержит демонстрационные учётные записи консольной версии;
они не являются администраторами Django. Для админки отдельно используется
`python manage.py createsuperuser`.

## Запуск веб-версии

```bash
source .venv/bin/activate
python manage.py check
python manage.py runserver --insecure
```

После запуска открыть <http://127.0.0.1:8000/>.

Сейчас в настройках установлено `DEBUG=False`. Флаг `--insecure` разрешает
учебному серверу Django отдавать собственные CSS, JS и изображение при этом
значении. Он используется только для локальной разработки. Если установить
`DEBUG=True`, достаточно обычного `python manage.py runserver`; для
неизвестных URL в этом режиме Django покажет диагностическую страницу 404.

## Текущее состояние и дальнейшее развитие

В ПР5 добавлены Django-проект, три приложения, двухуровневая маршрутизация,
view-функции, динамические URL, HTML, Bootstrap, навигация и обработка 404.
В ПР6 добавлены наследование шаблонов, include-компоненты и статические файлы.
В ПР7 реализованы реляционная SQLite-база, импорт JSON, SQL-выборки, поиск,
фильтры и статистика. Проверки не изменяют рабочую предметную базу:
веб-тесты используют временный SQLite-файл для каждого теста.

На следующих этапах планируются Django ORM, формы, веб-авторизация и
редактирование данных через браузер.
