# Сервис учёта бытовой техники

Учебный индивидуальный проект: реестр устройств, их характеристик,
размещения, состояния и рекомендаций по обслуживанию. Консольная версия
ПР1–ПР3 работает с JSON; веб-версия ПР5–ПР6 получила SQL-слой в ПР7,
а в ПР9 переведена на Django ORM. В ПР10 расширена административная панель,
добавлены типизированные состояния, slug, собственный QuerySet и анализ SQL.
В ПР11 добавлены пользовательские формы создания и редактирования техники,
списание через POST и загрузка фотографии помещения.

## Возможности веб-версии

- Списки помещений и техники, подробные карточки и связанные ссылки.
- Поиск по названию либо по названию, типу, производителю и модели.
- Совместные фильтры по помещению, состоянию и максимальной стоимости.
- Скрытие списанных устройств и поиск техники для обслуживания.
- Сортировка по названию, цене, году или помещению и названию.
- Пагинация по 2, 5, 10, 20 или 50 устройств с сохранением параметров GET.
- Помещения без действующей техники; списанная техника не занимает помещение.
- Статистика количества и стоимости, группировка по помещениям и состояниям,
  фильтрация групп по минимальному количеству устройств.
- Создание, изменение и удаление объектов через Django admin и Django shell.
- Inline-редактирование техники в помещении, редактирование цены и состояния
  прямо в списке, массовое списание и направление на обслуживание.
- Постоянные латинские URL помещений и вычисляемый базой год обслуживания.
- Проверка ввода, пустые результаты и страницы с HTTP 404.

## Технологии

Python 3.10+, Django 5.2, SQLite, Django ORM, DTL, Bootstrap 5.3.3,
CSS и JavaScript. Проверки: pytest, pytest-django, flake8, Pyright.
`django-stubs` описывает типы Django для статического анализатора.
Для ПР10 установлены Django Debug Toolbar 6.2.0 и Unidecode 1.4.0.
Текущее окружение и `pyrightconfig.json` настроены на Python 3.14.

## Установка и запуск

Из корня проекта, где находится `manage.py`:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py import_pr7
python manage.py check
python manage.py runserver --insecure
```

Открыть <http://127.0.0.1:8000/>. При `DEBUG=False` флаг `--insecure`
нужен учебному серверу для локальной отдачи статики. При `DEBUG=True`
достаточно `python manage.py runserver`. Bootstrap загружается с CDN.

Создание администратора:

```bash
python manage.py createsuperuser
```

Далее открыть <http://127.0.0.1:8000/admin/>. Администраторы Django
и пользователи предметной области — отдельные учётные записи.
Пользователи из JSON не получают права входа в admin автоматически.

## Модели ПР9–ПР10

| Модель | Приложение | Поля и ограничения |
|---|---|---|
| `Room` | `rooms` | `id`, уникальное обязательное `name`, автоматически формируемый уникальный `slug` |
| `Condition` | `conditions` | `id`, уникальные `code` (TextChoices) и русское `name` |
| `User` | `users` | `id`, уникальный `login`, `password` с хешем Django |
| `Device` | `equipment` | `id`, `name`, `device_type`, `manufacturer`, `model`, `purchase_year`, `price`, `room`, `condition`, `service_interval`, вычисляемый `next_service_year` |

`id` создаётся Django как `BigAutoField(primary_key=True)`.
Обязательные поля не допускают NULL и пустого ввода (`null=False`,
`blank=False`). Интервал обслуживания по умолчанию равен 3 годам.
Исключение — автоматически формируемый slug: `blank=True`, `editable=False`.
Цена хранится как `DecimalField(max_digits=12, decimal_places=2)`.
Валидаторы проверяют год покупки от 1900 до текущего, неотрицательную цену
и положительный интервал. Ограничения БД дополнительно защищают цену,
минимальный год, интервал, непустые названия и допустимые состояния.

Связи «один ко многим»:

```text
Room      1 ── N Device: room = ForeignKey(..., PROTECT, related_name="devices")
Condition 1 ── N Device: condition = ForeignKey(..., PROTECT, related_name="devices")
```

Удаление используемого помещения или состояния запрещено `PROTECT`.
Прямые связи: `device.room`, `device.condition`; обратные:
`room.devices.all()`, `condition.devices.all()`.
`device.room_id` — числовой внешний ключ, `device.room` — объект модели.
Связь с пользователем не добавлялась: в исходном проекте ПР7 её не было.
Методы `is_available()` и `get_service_status()` сохраняют правила ПР3.

## Базы данных и перенос из ПР7

- `data/appliances.sqlite` — исходная база ПР7 с таблицами `rooms`,
  `users`, `conditions`, `devices`. Сохранена в репозитории как учебный источник.
- `db.sqlite3` — рабочая база Django: служебные таблицы и новые таблицы
  `rooms_room`, `users_user`, `conditions_condition`, `equipment_device`.
  Путь задан в `DATABASES`; файл исключён из Git.
- `data/*.json` — сохранённые исходные данные и хранилище консольной версии.

Выбрана стратегия создания новых таблиц миграциями и отдельного переноса.
Настройка `DATABASES` не переключается на исходный файл ПР7.
Команда `python manage.py import_pr7` вызывает `db.orm_import.import_pr7()`:

1. Открывает исходную SQLite-базу в `mode=ro` и проверяет внешние ключи.
2. Читает помещения, состояния, пользователей и устройства.
3. Сохраняет их через ORM в одной транзакции, в порядке зависимостей.
4. Сохраняет исходные ID, `room_id`, `condition_id`; цену приводит к Decimal.
5. Пароли пользователей преобразует в хеши Django.
6. Совпадающие записи при повторном запуске пропускает. Конфликт значений
   вызывает ошибку и откат всех вставок текущего запуска; перезаписи нет.

Другой источник можно указать явно:

```bash
python manage.py import_pr7 --source data/appliances.sqlite
```

До перехода созданы локальные резервные копии `db.sqlite3.pr9-backup`
и `data/appliances.sqlite.pr9-backup`. Они исключены из Git.
Перед ПР10 также создана копия `db.sqlite3.pr10-backup`.
JSON и исходная база не синхронизируются с рабочей ORM-базой:
редактирование в admin меняет только `db.sqlite3`. Повторный импорт после
изменения записи сообщает о конфликте, чтобы не затереть изменения.

SQL-код `db/database.py`, `db/import_json.py`, `db/queries.py`,
`db/check_queries.py`, `sql/schema.sql`, `sql/queries.sql` сохранён как
результат ПР7. Прямые SQL-запросы в текущих view-функциях отсутствуют.
В ПР9 SQL используется только для чтения старого формата при переносе
и в сохранённых учебных командах ПР7.

## Страницы

| URL | Назначение |
|---|---|
| `/` | Главная |
| `/devices/` | Список, фильтры, сортировка, пагинация |
| `/devices/<int:device_id>/` | Устройство, состояние, обслуживание |
| `/devices/search/` | Форма поиска, фильтры и постраничные результаты |
| `/devices/create/` | Создание устройства через ModelForm |
| `/devices/<int:device_id>/edit/` | Редактирование устройства |
| `/devices/<int:device_id>/retire/` | Списание, только POST |
| `/devices/statistics/` | Общая статистика, группировки, обслуживание |
| `/rooms/` | Помещения с количеством устройств |
| `/rooms/<slug:slug>/` | Помещение и связанные устройства, основной адрес |
| `/rooms/<slug:slug>/photo/` | Загрузка или изменение фотографии |
| `/rooms/<int:room_id>/` | Сохранённый совместимый адрес по ID |
| `/rooms/available/` | Помещения без действующей техники |
| `/admin/` | CRUD моделей через встроенную административную панель |

Примеры:

```text
/devices/?sort=room&page_size=5&page=2
/devices/?page_size=2&page=2
/devices/search/?q=Samsung&scope=all&room_id=2&condition=исправно&sort=price
/devices/?hide_retired=on&needs_service=on
/devices/statistics/?min_count=2
```

Сначала применяется поиск и фильтры, затем сортировка, затем `Paginator`.
Допустимые сортировки перечислены в `equipment.queries.SORT_FIELDS`;
произвольный параметр GET не передаётся в `order_by()`.
В сортировке есть `pk` как дополнительный ключ для стабильных страниц.
Форма при изменении фильтров сбрасывает номер страницы, а навигация сохраняет
остальные параметры. Нечисловой `page` открывает первую страницу,
нулевой, отрицательный или слишком большой — последнюю (`get_page()`).
На исходных трёх устройствах пагинацию можно увидеть, выбрав по 2 на странице.
Ошибки фильтров, сортировки и размера страницы показываются в форме.
Ненайденный объект возвращает HTTP 404. Пустые выборки обрабатываются
через `{% empty %}`. `icontains` безопасно экранирует SQL-метасимволы.
SQLite по умолчанию различает регистр кириллицы в LIKE, как и в ПР7;
например, для «Холодильник» следует искать «Холод».

Пример «свободные помещения на дату» из Roomly адаптирован к предметной
области: здесь нет бронирований и дат занятости. Поиск доступной техники
выполняется по состоянию «исправно», поиск свободных помещений — по
отсутствию несписанной техники.

## ORM-запросы и проверка минимального объёма

Запросы реализованы в `equipment/queries.py`, `rooms/views.py`,
`equipment/views.py`, `equipment/forms.py` и используются страницами.
Ниже перечислены различные выборки, а не отдельные методы одной цепочки.

| № | Выборка | Применение |
|---|---|---|
| 1 | `Room.objects.all()` | Помещения в форме поиска |
| 2 | `Device.objects.with_related()` → `select_related("room", "condition")` | Списки без N+1 |
| 3 | `.get(pk=device_id)` | Карточка устройства |
| 4 | `get_object_or_404(Room, slug=slug)` | Карточка помещения |
| 5 | `.filter(room=room)` | Фильтр техники по помещению |
| 6 | `.filter(condition__name=condition)` | Фильтр по связанной модели |
| 7 | `.filter(room=room, condition__name=condition)` | Совместные условия |
| 8 | `.filter(price__lte=max_price)` | Ограничение стоимости |
| 9 | `.active()` → `.exclude(condition__code=Condition.Code.RETIRED)` | Скрытие неактуальной техники |
| 10 | `.filter(name__icontains=term)` | Поиск по одному полю |
| 11 | `.filter(Q(...) \| Q(...) \| Q(...) \| Q(...))` | Поиск по четырём полям |
| 12 | `.order_by("name", "pk")` | Сортировка по названию |
| 13 | `.order_by("room__name", "name", "pk")` | Сортировка по связанному полю |
| 14 | `Room.objects.annotate(device_count=Count("devices"))` | Карточки помещений |
| 15 | `room.devices.select_related("room", "condition")` | Обратная связь |
| 16 | `Device.objects.aggregate(...)` | COUNT, SUM, AVG, MIN, MAX |
| 17 | `Room.objects.annotate(...).filter(device_count__gte=...)` | Группировка и HAVING |
| 18 | `Condition.objects.annotate(...)` | Группировка по состояниям |
| 19 | `.needs_service()` → `exclude(...).filter(Q(...) \| Q(next_service_year__lte=year))` | Требующие обслуживания |
| 20 | `Room.objects.exclude(pk__in=active_room_ids)` | Помещения без действующей техники |
| 21 | `Condition.objects.values_list("name", "name")` | Только нужные поля для выбора состояния |
| 22 | `Paginator(queryset, page_size).get_page(page)` | Ограничение результата страницей |
| 23 | `.annotate(room_name=F("room__name"), ...).values(...)` | Таблица обслуживания одним запросом |

Для подзапроса доступности также используется `.values("room_id")`.
Списанные устройства исключены из стоимости действующей техники.
Агрегаты для пустой БД возвращают ноль, годы — `None`. LEFT JOIN,
используемый при аннотировании, сохраняет помещения и состояния без устройств.
Объекты для обслуживания исключают списанную и уже ремонтируемую технику.

## CRUD через Django shell

```bash
python manage.py shell
```

```python
from decimal import Decimal
from rooms.models import Room
from conditions.models import Condition
from equipment.models import Device

room = Room.objects.create(name="Тестовая мастерская")
device = Device.objects.create(
    name="Дрель", device_type="Инструмент", manufacturer="Bosch",
    model="GSR", purchase_year=2025, price=Decimal("5000.00"),
    room=room, condition=Condition.objects.get(name="исправно"),
)
device.name = "Шуруповёрт"
device.full_clean()
device.save(update_fields=["name"])
print(Device.objects.get(pk=device.pk).name)
device.change_condition("в ремонте")
device.save(update_fields=["condition"])
print(room.devices.all())
# room.delete() сейчас запрещён из-за связанного устройства (PROTECT).
device.delete()
room.delete()
```

Присваивание изменяет объект в памяти, `save()` сохраняет изменения.
`full_clean()` проверяет модель, но не вызывается автоматически из `save()`;
в admin проверку выполняет ModelForm, а импорт вызывает её явно.

## Структура проекта

```text
manage.py                  # команды Django
appliance_service/         # settings, urls, WSGI/ASGI
equipment/                 # Device, ORM-запросы, формы, страницы, admin
  migrations/              # версия структуры таблицы Device
  management/commands/     # команда import_pr7
  managers.py              # DeviceQuerySet и DeviceManager
rooms/                     # Room, страницы помещений, admin, миграции
conditions/                # Condition, admin, миграции
users/                     # User предметной области, admin, миграции
homepage/                  # главная, 404, static/homepage/{css,js,img}
  context_processors.py    # общие site_name и rooms_count
templates/                 # base, 404, includes/{navigation,pagination}
db/orm_import.py           # перенос из SQLite ПР7 в ORM
db/, sql/                  # сохранённый SQL-слой ПР7
models.py, devices.py      # предметные классы и логика CLI из ПР3
storage.py, main.py        # JSON и консольная версия

Все страницы наследуют `templates/base.html`; карточки и навигация вынесены
в include-шаблоны. ORM-объекты передаются через контекст в `render()`.
Связанные значения: `device.room.name`, `device.condition.name`.
Именованные URL, DTL-фильтры, экранирование, статика и обработка 404 сохранены.

python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py showmigrations

```

`-j 1` отключает создание рабочих процессов flake8, что удобно в ограниченном

## Административная панель ПР10

Все приложения, модели и поля имеют русские названия. Админка открывается
по `/admin/`; существующие учётные записи администраторов сохранены.

- Устройства: связанные помещение и состояние, цена, плановый год обслуживания
  и признак доступности; поиск по технике и помещению, фильтры по состоянию,
  помещению и типу, сортировка, по 10 строк на странице.
- `list_editable` позволяет менять цену и состояние в списке устройств,
  а название помещения — в списке помещений. Ссылки открытия карточек
  не пересекаются с редактируемыми полями.
- В форме устройства поля сгруппированы; помещение и состояние выбираются
  через `autocomplete_fields`; вычисляемый год доступен только для чтения.
- `DeviceInline` показывает устройства внутри помещения, позволяет изменить
  их состояние и цену, содержит ссылку на полную карточку. Пустые формы
  добавления и удаление из inline отключены.
- Действие «Направить исправные на обслуживание» меняет только исправные
  устройства; техника в ремонте и списанная пропускается.
- Действие «Списать выбранные устройства» меняет внешний ключ состояния,
  сохраняя запись и историю. Итоговое количество выводится через сообщения.
- В списке помещений показаны количество техники и ссылка «Открыть»;
  `get_absolute_url()` также обеспечивает ссылку «Посмотреть на сайте».
- Пользователи проекта сохраняют отдельную форму смены пароля с хешированием.
  `users.User` не подменяет встроенную модель администраторов Django.

Группы разрешений можно создать повторяемой командой:

```bash
python manage.py setup_admin_groups
```

«Наблюдатели техники» имеют 4 разрешения просмотра моделей проекта.
«Операторы техники» имеют 12 разрешений просмотра, добавления и изменения,
без удаления. Команда не назначает группы существующим пользователям.
В `/admin/auth/user/` администратор может создать сотрудника с `is_staff=True`
и назначить ему группу. Сам флаг `is_staff` не предоставляет права изменения.
Проверки разрешений распространяются и на массовые действия.

## Состояния, QuerySet и миграции ПР10

`Condition.Code` — перечисление `TextChoices`:

| Код | Название |
|---|---|
| `WORKING = "working"` | исправно |
| `SERVICE = "service"` | требует обслуживания |
| `REPAIR = "repair"` | в ремонте |
| `RETIRED = "retired"` | списано |

В `conditions/migrations/0002_condition_code.py` сначала добавляется временно
nullable-поле, затем `RunPython` по исторической модели заполняет коды по
прежним названиям, после чего вводятся обязательность, уникальность и CHECK.
ID состояний и внешние ключи устройств сохраняются. Поле `name` оставлено
для совместимости с JSON, SQL ПР7 и прежними шаблонами; при сохранении модели
название определяется по коду. Правила доступности и статистики используют
константы `Condition.Code`.

В этой предметной области отсутствовало булево поле отмены бронирования:
миграция адаптирована к существующему справочнику состояний техники.
`DeviceQuerySet` и `DeviceManager` реализуют `active()`, `working()`,
`in_repair()`, `retired()`, `with_related()`, `needs_service()` и выборку
по помещению через `for_room()`. Методы возвращают QuerySet и комбинируются
с `filter()`, `order_by()` и `values()`; обращения к БД остаются ленивыми.
`objects.all()` сохраняет все устройства, включая списанные. `active()`
означает «не списано», а доступность для использования — только `working()`.

```python
from equipment.models import Device

Device.objects.working().for_room(1).order_by("price", "pk")
Device.objects.active().filter(manufacturer__icontains="Samsung")
Device.objects.needs_service(2026).with_related()
```

`Device.next_service_year` — `GeneratedField` с выражением
`F("purchase_year") + F("service_interval")` и `db_persist=True`.
Он введён миграцией `equipment/0002_device_next_service_year_and_more.py`.
После изменения исходных полей и `refresh_from_db()` значение отражает
результат вычисления SQLite. Это рекомендация по возрасту: полноценная
история дат ремонта в проекте не ведётся. Уже ремонтируемая и списанная
техника исключены из списка обслуживания.

`rooms/0002_room_slug.py` добавляет slug, заполняет существующие помещения
через `slugify(unidecode(name))` с суффиксом `-<id>`, затем вводит уникальность.
Для новых объектов `save()` формирует адрес в транзакции. Переименование
помещения не меняет уже опубликованный URL. Например: `/rooms/kukhnia-1/`.
Старые URL по ID сохранены. Основные ссылки шаблонов используют
`room.get_absolute_url()`, а представление — `get_object_or_404()`.

Контекстный процессор `homepage.context_processors.site_context` передаёт
название сайта и актуальное количество помещений в общую навигацию.
Подсчёт выполняется одним запросом на рендер страницы; глобального кэша нет.

## Django Debug Toolbar и анализ SQL

Для локального запуска с панелью:

```bash
source .venv/bin/activate
DJANGO_DEBUG=1 python manage.py runserver
```

Открыть <http://127.0.0.1:8000/devices/> и выбрать панель SQL справа.
В этом режиме подключаются приложение `debug_toolbar`, middleware
и маршруты `/__debug__/`; разрешены только локальные IP. По умолчанию
`DJANGO_DEBUG` выключен, панель и её маршруты не подключаются.

Проверены не только наличие панели в HTML, но и получение содержимого SQLPanel
через `/__debug__/render_panel/`: ответ HTTP 200 содержит SQL таблицы устройств.
В списке устройств связи загружаются через `select_related()`.
Для таблицы обслуживания `annotate(F(...)).values(...)` выбирает нужные
колонки сразу одним SQL-запросом; `select_related()` для этой проекции не нужен.

Воспроизводимый анализ без изменения записей:

```bash
python manage.py profile_orm
python manage.py profile_orm --output /tmp/pr10-sql.json
```

Команда сравнивает неоптимизированный пример с рабочей загрузкой связей,
затем измеряет реальные HTTP-сценарии через Django Client и
`CaptureQueriesContext`. На исходных трёх устройствах обычный перебор связей
выполнил 7 SQL-запросов, `with_related()` — 1. Публичный список выполняет
5 запросов: состояния формы, COUNT пагинатора, общий счётчик помещений,
варианты помещений и выборку текущей страницы с JOIN.
Число запросов не увеличивается при росте количества карточек на странице.
Подробные результаты: [docs/PR10_SQL.md](docs/PR10_SQL.md).

## Формы и фотографии ПР11

`equipment.forms.DeviceForm` — ModelForm с явным списком редактируемых полей.
Форма позволяет создать или изменить устройство, выбрать помещение и указать
необязательное многострочное примечание `notes`. При создании состояние
назначается сервером как `WORKING`; поля `condition`, `id`, `next_service_year`
не принимаются из POST. Текущее состояние показано отдельным disabled-полем,
год покупки в пустой форме подставляется автоматически.

`DeviceSearchForm` и `StatisticsForm` сохраняют GET-фильтрацию, сортировку
и пагинацию. Все формы оформлены через Bootstrap; общий include
`includes/form_fields.html` выводит label, widget, help_text, ошибки полей
и `non_field_errors`. Отправленные значения остаются в невалидной форме.

Серверные проверки:

- обязательные поля, типы, неотрицательная цена и положительный интервал;
- `clean_name()` нормализует пробелы и требует минимум два символа;
- `clean_purchase_year()` допускает год от 1900 до текущего;
- `clean()` запрещает дубликат названия в выбранном помещении;
- при редактировании текущий ID исключается из проверки дубликата;
- списанное устройство нельзя переместить в другое помещение.

Это адаптация задания с бронированиями: в учёте техники проверяется год
покупки и конфликт названия в помещении, а календарь бронирований не создаётся.
При ошибке IntegrityError форма показывает общее сообщение, а транзакция
не сохраняет частичные изменения. После успешного сохранения используется
POST/Redirect/GET с сообщением об успехе и переходом на карточку устройства.

Списание выполняется отдельной формой на карточке устройства и меняет
состояние на `RETIRED`, сохраняя запись. GET на ручку списания возвращает 405,
повторное списание безопасно. POST-формы содержат CSRF-токен.

Создание требует `equipment.add_device`, редактирование и списание —
`equipment.change_device`, изменение фотографии — `rooms.change_room`.
Анонимный пользователь перенаправляется на вход в admin; пользователь без
нужных прав получает 403. Войдите на `/admin/login/` и затем откройте
публичную часть сайта: кнопки появляются согласно разрешениям. Группы ПР10
можно назначить сотрудникам через административную панель.

В модель Room добавлен `photo = ImageField(...)`, форма `RoomPhotoForm`
принимает `request.FILES`, шаблон использует `multipart/form-data`.
Поддерживаются JPEG, PNG и WebP размером до 5 МБ; Pillow проверяет, что файл
является изображением. Отдельная форма дополнительно проверяет декодированный
формат. Файл получает случайное имя; в БД хранится относительный путь,
публичная карточка помещения использует `room.photo.url` только при наличии
изображения. ImageField также доступен в admin. При замене фотографии старый
файл автоматически не удаляется, поэтому его можно восстановить.

`MEDIA_ROOT` указывает на локальную `media/`, `MEDIA_URL` — `/media/`.
Медиафайлы исключены из Git. Для локальной отдачи фотографий нужен режим:

```bash
DJANGO_DEBUG=1 python manage.py runserver
```

В рабочем окружении с `DEBUG=False` отдачу медиа настраивают отдельно;
`--insecure` относится к staticfiles, а не к загрузкам пользователей.
Новые зависимости устанавливаются через `pip install -r requirements.txt`;
для ImageField добавлен Pillow. Миграции ПР11: `equipment/0003_device_notes`
и `rooms/0003_room_photo`. Перед применением сохранена
`db.sqlite3.pr11-backup`, исключённая из Git.

Проверка ПР11: 158 тестов, включая 19 новых проверок форм, прав, CSRF,
дубликатов, редактирования, списания и загрузки изображений. Фактические
снимки интерфейса получены браузером на отдельной копии базы и находятся
в `reports/evidence/`; рабочие записи при подготовке отчётов не менялись.

Отчёты ПР9, ПР10 и ПР11 подготовлены в `reports/` по предоставленному образцу.
